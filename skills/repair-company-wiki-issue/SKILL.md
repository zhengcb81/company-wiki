# 修复一项 CWP 来源问题

输入为本仓 issue、专用观察，或一个可读的本仓原生回执。未指定条目时从本仓[反馈计划](../../docs/plans/feedback-loop-2026-11-17/company-wiki.md)及相邻 issues 中选一个已确认影响主线的问题。以 issue 的原发现方、run、attempt、原件 SourceRef 和定位为起点。实际原始文件的位置由来源端口解析。

1. 对照原生检查的预期与实际，找出第一处偏离。旧版 Phase C 完成回执可用 `python -m tools.document_understanding_benchmark.phase_c_feedback <overall.json> --ref <evidence_ref>` 离线复核。记录运行模式、选择器版本、执行版本和内容 SHA 各自能证明的范围。未知付费先走原生产侧只读对账。

   涉及真实拒绝时，在编辑前核对原门禁保护的事实、所属入口、同类合法输入和确实越界的反例。重复检查和表示限制从责任入口删除。必要的检查收窄到实际动作和必需字段。将删除、收窄、保留或待取证的判断、理由和复现引用记入同一问题或 PWF。已确认的必要拒绝走原处置。

2. 在一个隔离临时目录从公开入口写出最小 RED，同时找一个相似但合法的样本。涉及摘要时比对原文位置、说话人、时间、条件和否定。已选择引用回原文、自动选材以及正式生成分别验证。若问题属于调用方的请求、会计计算或界面投影，提供公开输入、输出和应满足的合同，保留原发现方等待回告。
3. 找拥有该行为的组件，把共用根因、受影响的接口和验收范围加入本仓现行 PWF。重复的限额或表示许可在责任层消除，来源验真和实际配置的预算照常执行。修复使用通用输入及公共端口。先跑刚才的 RED 和合法对照，再跑受影响的现有测试。
4. 对原场景重新读修复版本。内容类问题增加另一文种或公司，跨仓问题要求发现方说明实际消费的内容 SHA、定位和产物。若 RF 使用来源，借助报告、快照及驱动/收入公式验证真实采用。定位回放通过只验来源，不能推出投资结论。复验有新问题时用新 attempt 追加事实。
5. 在同一 issue 下关联实施提交、测试、发现端复验的版本和证据。已有票据只增加一次发生。大节点由独立审查者验证可复现性、误报、原件保护和清理，再更新 PWF。保留原来的失败记录，并注明尚待真实验证的范围。
