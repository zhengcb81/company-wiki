## 执行摘要：五个最尖锐的发现

1. **系统在"假装运行"**：每天采集数百篇新闻，dashboard显示"健康度100/100"，但核心指标"LLM总调用: 0"。采集→ingest→分析的全链条中，后两段基本死寂。
2. **改进计划工程化率为零**：`docs/系统审查与改进计划.md`制定了30天详细路线图，但log.md中没有任何执行记录。文档写得越漂亮，反差越刺眼。
3. **"零成本陷阱"是核心设计错误**：为省API费用，矛盾检测、投资判断、PDF分类等5个关键模块用正则实现，结果产出垃圾，反而浪费了存储和清理成本。这是典型的 false economy。
4. **信息熵增而非复利增长**：llm-wiki.md要求的是"知识随每次ingest变 richer"，实际却是"raw进、垃圾堆、wiki膨胀不可读"。北方华创366行、光模块450条目，但信息密度在稀释。
5. **从股票分析师视角，wiki目前不可用**：东方电缆的"综合评估"仍是2014年招股书观点；核心问题全部标记"[陈旧]"却无人更新；行业wiki来源全是"未知来源"。这不是知识库，是信息坟场。

## 一、对照 llm-wiki.md 理念的结构性差距

llm-wiki.md 的核心主张是：**wiki 是一个持久、复利增长的产物（persistent, compounding artifact）**。其理想状态是：

```
采集 → LLM深度理解 → 整合进已有知识网络 → 交叉引用、矛盾标记、综合更新
```

你的实际状态是：

```
采集 → 正则提取/标题复制 → 按时间线append → wiki膨胀 → 事后清理
```

**关键差距：**

| llm-wiki.md 要求 | 你的现状 |
|---|---|
| "LLM增量构建和维护wiki，人类负责策展和提问" | LLM在核心模块被禁用（正则替代），人类变成垃圾清理工 |
| "矛盾已经被标记，综合已经反映所有读过的内容" | 矛盾检测200潜在、0高置信；综合评估31页缺失、大量过时 |
| "Ingest一条新闻可能触及10-15个wiki页面" | 交叉污染清洗移除了3,886条跨行业错误条目，说明相关性判断机制失效 |
| "Lint保持wiki健康" | lint发现的问题没有触发任何自动修复或人类审核流程 |
| "Index.md帮助导航，log.md记录操作" | log.md被"测试问题？"污染80+次，index.md中公司描述大量是过时的研报摘要 |

llm-wiki.md 中还有一个关键洞察：**"The tedious part... is the bookkeeping. Humans abandon wikis because the maintenance burden grows faster than the value."**

你的项目恰恰反其道而行：LLM被剥夺了bookkeeping权（正则替代），导致维护 burden 全部落在了人类（或maintenance.py这种事后清理脚本）身上。这不是llm-wiki，这是"正则提取+事后救火"。

## 二、对照 设计思想.md 的意图偏离

设计思想.md 明确要求：

> "4，以上知识库系统要有自我进化能力...具体实现可以参考llm-wiki.md文档"
> "不要做任何头痛医头，脚痛医脚的改进，而是要从机制上、设计上把项目打造成可以自我进化的动态的知识库"

**实际运行的"自我进化"模块状态：**

| 模块 | 声称功能 | 实际状态 |
|---|---|---|
| `auto_discover.py` | 自动发现新实体/主题 | 输出全是垃圾 |
| `evolve_questions.py` | 动态进化问题清单 | schema_evolve只产出了"8指标/424chars"的空洞建议 |
| `event_bus.py` + `job_queue.py` + `repair_planner.py` | 闭环反馈系统 | **零订阅者/零消费者**，发布端存在，消费端不存在 |
| `state_store.py` | 系统状态追踪 | **只读取不写入** |
| `investment_judgment.py` | 生成结构化投资判断 | 纯正则提取，无分析价值 |

这是**架构层面的自欺欺人**：代码里有一堆听起来很厉害的模块名（event_bus、job_queue、repair_planner、closed_loop_dashboard），但它们之间没有真正的数据流。就像造了一辆车，有发动机舱、有油箱、有仪表盘，但发动机不点火、油管不接、仪表盘显示固定值"100km/h"。

`dashboard.md` 就是最典型的例子：
- 系统健康度：🟢 100/100
- LLM总调用: 0
- 任务队列：0待处理/0运行中/0已完成/0失败
- 解析错误率: 0.0%

一个LLM调用为0、任务队列为空、日志被测试查询污染的系统，健康度100/100。这不是监控，这是安慰剂。

## 四、从股票分析师角度的可用性审判

假设我现在要基于这个知识库做投资决策，看看我能得到什么：

### 案例1：东方电缆（被压缩后的页面，66行）

**优点：**
- 有"关键判断"、"核心矛盾"、"投资论点"三段式结构，格式正确。
- 矛盾被结构化提炼（营收增长vs毛利率下滑、技术突破vs盈利兑现）。

**致命缺陷：**
1. **综合评估仍是2014年招股书观点**："当前时点（2014年），公司正面临陆缆业务盈利下滑和海缆业务青黄不接的困境"。这是2026年的wiki页面，综合评估停留在2014年。
2. **核心问题全部"[陈旧]"**：5个核心问题从海缆竞争、高压直流研发、财务指标、海上风电驱动等角度提问，但都标记为陈旧，且没有新问题替代。这意味着系统没有根据2025-2026年的新信息（如海上风电装机量爆发、数据中心电力需求增长）动态更新问题清单。
3. **时间线条目质量差**：2026-04-12的"最新动态"条目内容空洞（"高端海洋能源装备系统应用示范项目码头...2026.03.16"），没有提取关键信息（订单金额、项目意义、竞争格局变化）。
4. **矛盾警告未整合**：页面上堆积了5个`[!warning]`框，内容重复（多次提到"营收增长但应收账款增长更快"），没有被综合为一条清晰的判断。

**结论**：如果我是分析师，看完这个页面后，我仍然需要自己去读原始新闻和财报，因为wiki没有提供"这是好消息还是坏消息？对估值有什么影响？"的投资级判断。

### 案例2：半导体代工行业wiki（103行）

**问题：**
- 88条时间线中，**来源类型全部是"未知来源"**。这在投资研究中不可接受——任何数据都需要可追溯。
- 时间线是按"条目"而非"事件"组织的。例如"台积电2nm产能排满至2028年"和"台积电2025年CoWoS产能至少翻一番"是两个独立条目，但没有被整合为"台积电先进制程与封装双扩产"的综合判断。
- 综合评估虽然存在，但只是信息罗列，没有给出"这对中芯国际是利好还是利空？对设备厂有什么连锁影响？"的推理。

### 案例3：投资估值页面（东方电缆）

这个页面完全失败：
- 只是把PDF中的财务数据用正则提取成了表格。
- 没有估值模型（PE、PB、DCF、EV/EBITDA）。
- 没有与同行（中天科技、亨通光电）的估值对比。
- "趋势分析"只有一句话："从X亿元→Y亿元（增长趋势）"。这是小学生水平的分析，不是投资研究。

## 五、根本性机制缺陷（为什么多轮改进都失败）

`系统审查与改进计划.md` 中有一句深刻的诊断：

> **"信息流是熵增的。每一层都不可逆、不可重处理、不可验证。wiki会越膨胀越不可读，但原始信息已经损失——这就是'为什么多轮改造仍然失败'的根因。"**

这个诊断完全正确。让我进一步拆解为什么信息会变成熵增：

### 缺陷1：没有"验证-压缩-淘汰"的熵减机制

当前管道：
```
PDF → 一次LLM摘要（或正则提取） → wiki条目（原始信息99%丢弃）
```

理想的llm-wiki管道应该是：
```
采集 → 提取信号 → 验证 → 压缩为判断 → 淘汰过时信息
```

你的系统只有前半段（采集→提取），后半段全缺。所有的"进化模块"（event_bus、job_queue、repair_planner）只在做前半段的事——它们不压缩、不淘汰、不产生判断。

**具体表现：**
- 时间线条目无限append，没有自动归档或综合机制（虽然consolidate.py存在，但它是事后被动触发，而非过程中的质量控制）。
- 综合评估一旦生成就不再更新（东方电缆2014年招股书评估至今仍在）。
- 矛盾检测发现了200个潜在矛盾，但没有触发任何"淘汰过时条目"或"更新综合评估"的动作。

### 缺陷2："零成本陷阱"的级联效应

为节省LLM API成本，5个关键模块用正则替代：
1. `pdf_extract_v2.py:248` 把半年报/季报全标为 `annual_report`
2. `investment_judgment.py` 纯正则提取，产出"投资估值"这种无分析页面
3. `contradiction_detector.py` 1,366,522潜在矛盾→0高置信度
4. `cross_verify.py` 89.6%单来源，虚假聚类
5. `auto_discover.py` 输出垃圾

**级联效应：**
- PDF分类错误 → 财报日期全错（半年报日期变成12-31）→ wiki时间线混乱 → 矛盾检测发现大量虚假矛盾 → 分析师无法信任数据
- 投资判断用正则 → 产出无价值页面 → 股票分析师放弃使用wiki → 系统失去用户反馈 → 进一步退化

这就像一个工厂为了省电关了质检环节，结果产品全部报废，最终损失远超电费。

### 缺陷3：配置系统的碎片化是架构癌

4套并行配置读取机制：
1. `Config` dataclass
2. 直接 `yaml.safe_load`
3. `RulesConfig`
4. `graph.yaml`

后果：
- `collect_news.py:371` 查 `"tavily_api_key"`，`Config` 返回 `"api_key"` → API key 永远读不到
- 新闻采集模块实际不可用，但系统没有报错（因为可能从其他路径读到了？或者根本没有运行？）
- 新开发者（或LLM agent）无法判断该用哪套配置

这是**架构层面的技术债务**，不重构配置系统，任何新功能都会在基础上摇摆。

### 缺陷4："全覆盖"战略导致"零深度"

241家公司，但只有约10%（~24家）有实质wiki内容。其余230+家只有几条空泛新闻。

**从投资研究角度，这是错误的战略。** 覆盖241家每家3条新闻，不如深度覆盖30家每家50条高质量分析。深度覆盖意味着：
- 每家公司有完整的时间线（>20条有信息增量的条目）
- 每家公司有更新的综合评估（基于最近财报/新闻）
- 每家公司有投资论点（估值、催化剂、风险）
- 行业页面能基于公司数据产生真正的产业链分析

你的系统目前在做前者（广覆盖、浅分析），而股票分析师需要的是后者。

## 六、系统性改进建议（从机制设计层面）

以下建议不是为了修复某个具体bug，而是为了重构系统的**信息动力学**，让它从"熵增"变成"复利增长"。

### 建议1：实施"三层数据架构"（来自系统审查与改进计划.md，必须执行）

```
Layer 1: raw/PDF         — 原始文件，不可变
Layer 2: extracts/MD     — 全文无损转换，保留页号
Layer 3: segments/SQLite — 标签化分段（实体/内容类型/时间/来源），不删减原文
         ↓
        wiki 合成（可重跑、可换策略）
```

**为什么这是机制性改进：**
- **可重处理**：换了分析框架（比如从"国产替代"视角切换到"全球竞争"视角），不需要重新读PDF，从Layer 3重新合成即可。
- **可验证**：Layer 2可逐页对照原件，Layer 3可逐段对照Layer 2。
- **信息不坍缩**：标签只做索引，原文无损保留。当前系统最大的问题是"一次LLM摘要后原始信息99%丢弃"，三层架构解决了这个不可逆性。

### 建议2：关键模块必须用LLM，禁止正则替代

如果成本是问题，**减少公司数量**（从241家聚焦到30-50家核心公司），而不是降低质量。投资研究是"高信噪比"场景，一条错误的判断可能比没有判断更危险。

**必须基于LLM的模块：**
- PDF分类与日期提取（`pdf_extract_v2.py`）
- 投资判断（`investment_judgment.py`）
- 矛盾检测（`contradiction_detector.py`）
- 实体发现（`auto_discover.py`）
- 交叉验证（`cross_verify.py`）

### 建议3：建立真正的"熵减"机制

**A. 自动综合触发器**
- 当公司wiki时间线条目超过50条时，自动触发LLM综合评估更新（不是简单的consolidate，而是重新写"关键判断+核心矛盾+投资论点"）。
- 当行业wiki条目超过100条时，自动触发行业综合报告。

**B. 信息半衰期标注**
- 每条时间线条目标注"信息有效期"（如：订单公告→有效期1年；行业政策→有效期2年；技术突破→长期有效）。
- 定期（每季度）扫描过期条目，不是删除，而是归档到`archive/`并更新综合评估。

**C. 核心问题动态进化**
- 当前核心问题全部"[陈旧]"，说明`evolve_questions.py`失效。
- 建议改为：每季度由LLM基于最新时间线，判断现有问题是否已回答/过时，并建议3-5个新问题。
- 新问题的建议必须写入`review_queue.md`，由人类（股票分析师）审核后采纳。这实现了"人类策展+LLM建议"的llm-wiki模式。

### 建议4：从"全覆盖"转向"深覆盖"

**立即行动：**
1. 将241家公司分为三类：
   - **Tier 1（核心，20-30家）**：半导体产业链上下游（从设备、材料、代工、设计到应用）+ 新能源产业链。这些必须有完整的wiki、更新的综合评估、投资判断。
   - **Tier 2（关注，50-80家）**：有定期新闻采集，但只在有重大事件时更新wiki。
   - **Tier 3（观察，其余）**：只保留目录结构和基本信息，暂停新闻采集和ingest，待Tier 1/2稳定后再扩展。

2. 将节省下来的API预算（从241家减少到30家深度覆盖）投入到：
   - Layer 2/3建设（一次性成本$200-400）
   - LLM综合评估更新（每季度）
   - 行业wiki的深度分析

### 建议5：废弃"幽灵模块"，重建真实闭环

**删除（不是保留）：**
- `event_bus.py`（零订阅者）
- `job_queue.py`（零消费者）
- `repair_planner.py`（无人调用）
- `closed_loop_dashboard.py`（被`quality_dashboard.py`替代但同样虚假）

**重建真正的闭环：**
```
ingest → lint（发现矛盾/断链/孤儿页面）→ 人类审核队列 → 修复 → 更新index.md → 记录log
```

关键变化：**lint发现的问题必须进入人类的待办清单**，而不是打印在报告里就结束。可以用`review_queue.md`或GitHub issues作为待办清单。

### 建议6：统一配置系统，建立"单一事实来源"

1. 所有公司/行业/主题数据 → `graph.yaml`（已经是这样，但需要清理）
2. 所有运维配置（API key、调度、路径） → `config.yaml`
3. **删除**其他两套配置读取机制（直接`yaml.safe_load`和`RulesConfig`）
4. `Config` dataclass 统一封装所有配置读取，提供强类型和默认值

### 建议7：改革监控指标，让dashboard说真话

当前`dashboard.md`的指标全是假的。建议改为：

| 指标 | 当前值 | 健康阈值 | 说明 |
|---|---|---|---|
| 昨日LLM调用数 | X | >50 | 核心模块必须用LLM |
| 昨日ingest条目数 | Y | >0 | 采集后必须ingest |
| 综合评估更新率 | Z% | >90% | 核心公司评估必须最新 |
| 高置信度矛盾数 | N | 0 | 有矛盾必须解决 |
| 断链数 | M | 0 | lint发现必须修复 |
| 核心问题陈旧率 | P% | <20% | 问题清单必须动态进化 |

**如果任何指标跌破阈值，健康度不应是100/100，而应该是红灯。**

## 结语

这个项目有极好的**设计意图**（llm-wiki.md的理念、设计思想.md的愿景、系统审查与改进计划.md的技术路线），但**执行层面严重脱节**。

最大的危险不是代码有bug——bug可以修。最大的危险是系统正在制造一种**"虚假繁荣"**：每天运行、每天采集、dashboard全绿，但实际上没有产出任何投资级价值。这种虚假繁荣会让你误以为系统在正常工作，从而延迟真正的改进。

**作为一个股票分析师，我目前不会使用这个wiki来做任何投资决策。** 因为：
- 综合评估过时（东方电缆2014年观点）
- 核心问题陈旧（全部标记"[陈旧]"）
- 投资判断缺失（正则提取的财务表格不是判断）
- 来源不可追溯（行业wiki"未知来源"）
- 矛盾未解决（堆积的warning框）

但如果按照上述系统性建议执行——特别是三层数据架构、关键模块LLM化、熵减机制、从全覆盖转向深覆盖——这个知识库有潜力成为真正的"复利增长"的研究助手。

**关键转折点：停止写更多改进文档，开始执行已有的改进计划。** 哪怕只执行`系统审查与改进计划.md`的Phase 1（止血，5天），系统状态也会有质的飞跃。
