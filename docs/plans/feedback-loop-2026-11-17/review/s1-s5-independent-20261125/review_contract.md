# 分仓复审口径

每个 owner 以本仓共享的 S1 事件清单、S2 统一日志、S3/S4 分仓交付和完整设计、S5 计划及上一轮台账为输入。一组测试通过，只证明该行为对给定版本、入口和条件成立。

## S1–S5

| 项目 | 核对要求 |
|---|---|
| S1 | 核实本仓历史黑洞和后续补修是否仍有效。重点看原异常保留、退出码与机器 stdout、子进程输出、脱敏和已收响应避免重复付费。无独立 S1 卡可标为不适用，并说明 S2 后实际补齐的场景。 |
| S2 | 核对操作开始、主要步骤、外部副作用及终态能否重建。检查本地有界日志与 F4 投影、稳定运行/尝试/步骤、时间、输入引用和版本、异常因果及位置、拒绝或诊断介质故障。验证公开冷读、重投和强停场景可用原身份，日志/反馈失败保留原业务结果。 |
| S3 | 核对生产及在用工程入口的公开跨仓契约、同仓 owner 封装、私有字段/SQL/配置穿透、实际运行环、路径注入和巨模块的职责。至少指出一个有具体后果的耦合或说明在分析范围内为何成立。区分纯值公共契约、兼容 shim、注解和真实运行依赖。 |
| S4 | 查实际日常 CI 收集与仓内边界约束能否拦截已经复现的绕行或丢日志。指出测试口径、平台及遗漏。无需引入生产许可，静态命中须人工验证。 |
| S5 | 对照本仓的具体修复，核对已发布提交、运行位置和受管安装如适用。区分已通过的定向回归、还没证明的全入口/仓内结构和当前复现的新缺口。 |

## 证据与输出

- 记录实际运行目录与精确 Git SHA，检查相关未提交路径。如有差异，注明测试基于已提交包或实际文件。环境缺证与功能失败分别写明。
- 选正在用的公开入口做小范围验证，优先一条正常基线和一条真实故障注入后的冷读。可复用经过核对的离线测试。若能安全地补一条原创反例，说明输入、触发条件、预期、观察、退出/计数和复现路径。避免费用、外部下载、生产写入和大矩阵。
- 按五项列“已验、部分、缺失、未证或不适用”及适用范围。另列关键发现，分别写影响、路径行号、实际复现或源码证据、根因、后续验收。把稳定数据契约和真实业务失败区分清楚。主流程有正常终态时，也核对同一关联号能否追溯关键步骤。
- 写入 `modules/<owner>.md`，使用中文。每个 agent 只写自己的报告与唯一临时目录，不编辑总控文件。重要发现先发给总控；仓库保持原状。
