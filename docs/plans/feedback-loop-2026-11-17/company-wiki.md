# CWP 资料阅读与反馈试点

工作目录为 `Projects/company-wiki`，本仓公开产品只管理来源、定位和解析质量。ROOT 同时维护 `tools/feedback_loop/` 的工程调度，工具隔离于 `src/company_wiki` 产品。P1 继续在[业务父计划](../du11-source-closure-2026-10-18/task_plan.md)实施。

1. 先以 `tools/document_understanding_benchmark/phase_c_runner.py` 的真实 Phase C 终态回执观测来源/缓存检查，用 `run_id` 和原生选择版本定位。记录实际成本可知性，成功退出不推导内容读全。支持独立 E2E 指定专用反馈输出；未提供输出时沿用旧调用和结果。缺证据映射 `unknown`。夹具包含真实回执结构、合法缺测、故意破坏缓存重放证明、反馈输出写失败仍保留原业务终态。
2. 在阅读策略/公开选材边界记录版本、选段定位、实际选择与被压过的原始业务信息。原语言摘要单列生成、选中支持和发言人/主体/程度/条件。固定半年报先冻结 12 项原文检查、再自动选卡，跨文种使用投资者关系问答。新问题记录为 `company-wiki` 的本仓条目，原文只用 SourceRef 和 locator。
3. `repair-company-wiki-issue` 从具体信号定位到来源、读取、选择、投影或恢复责任；适用的最小回放在隔离测试库中进行。先测 64 MB 重复预算和真实超限的区别、问句/答句相似合法对照，按本次风险选用。业务切片避免公司词典和提高限额的特判。技能写本仓 PWF 和 regression ID。
4. ROOT 负责实际模型版本及预算、正式新摘要、同 run/跨 run 恢复。让 RF 通过公开消费端取同一个新版本，并给出真正被采用的证据。将已使用旧缓存的失败例及新版本成功例隔离验证。来源 token、费用、字节数、保护目录和测试清理一次核验。内容、恢复和消费的大节点由独立 reviewer 对照原件定位及真实回告。

验收需分别报告选材覆盖、归属与限定、生成/缓存实际调用、哪个 RF run 用了哪个版本。仅指定已有 claim 回原文、仅离线模拟、仅调度协议通过的情况分别记其实际范围。

真实采用对照[11 月 14 日 RF 实例](../du11-source-closure-2026-10-18/review/phase-c-h1-formal-20261114.md)。用相同内容 SHA 追到具名经营证据、增长驱动和收入公式，再验证公开报告、快照和敏感性正控。隔离库的本地版本 ID 可以不同。执行修复代码版本、生成结果内容版本和 RF 实际采用分别留证。

首批三个原生检查只分别表达完整定位回放、同 run 的 POST 计数和跨 run 的 POST 计数。零 POST 单独不能证明读到了正确的缓存内容。完整恢复和内容质量依此处 F3 的真实结果验证。按原始工程作业绑定的 overall.json 可复查模式、选择器和内容版本；各仓作业端的自动引用解析由 F2 接入。
