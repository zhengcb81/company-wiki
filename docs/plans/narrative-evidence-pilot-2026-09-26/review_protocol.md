# 审查、放行与回滚规程

> 配套 [execution_cards.md](execution_cards.md) 和 [test_acceptance_plan.md](test_acceptance_plan.md)。**审查频率以 [G0–G4 大节点修订](milestone_review_cadence.md)为准**；下文逐卡清单是断言库，不要求逐卡独立审查或重复测试。本轮 F0–F5 已另获授权，Worker 仍暂停。

## 1. 每个大节点的可审材料

实施者在 G0–G4 相应大节点提交一份简短 `review_receipt`（放在本专题实施记录中，不写进其他正在执行的计划）：

```yaml
gate: G1  # G0..G4；物理迁移/删除各有独立批次
scope: "本节点实际交付及放行范围"
base_commit: "Git SHA"
contract_version: "本节点输入/代码/模型合同版本"
input_manifest_sha256: "冻结样本或删除批次 SHA"
checks: [{cmd: "关键命令", exit_code: 0}]
metrics: {quality: "分母+分子", latency: "p95", bytes: "同卷净变化"}
known_failures: ["未解问题与严重性"]
rollback: "关闭开关/撤回产物/恢复路径"
production_touched: false
worker_pause_preserved: true
decision: accepted_scoped  # 或 changes_required / blocked_decision
```

关键项空白或无法重跑则该节点不能放行。审查者查看实际 diff、关键测试报告和分层原文抽样；普通子步骤只保留实施者自检日志。修复后更新同一节点收据并重跑受影响检查，不复制全部历史命令输出。

## 2. 两层审查

| 层 | 执行者与必看证据 | 必须回答的问题 |
|---|---|---|
| **日常实现自检** | 实施者看受影响 diff、目标测试退出码及 temp 路径；无需独立签收 | 修改是否仅在允许范围？输出能否回源？ |
| **G 节点独立复审** | 未编写该节点核心代码的人核关键 diff/指标/收据；分层抽正、负和对抗样本 | 测试能否抓到误收、漏收、无来源摘要或并发失序？旧消费者和暂停状态是否保留？ |

G0/G2/G3/G4 分别让对应接口、运营或来源所有者审查其实际变更；已经在 revenue-forecast、R4、Worker v5 审过的同版本合同复用其收据，不重复签字。缺正式消费者合同则仅阻断该消费者切换。审查者可要求最小失败复现；实现者不能自己签大节点独立复审。

[原文处置 D0–D5](raw_disposition_plan.md)在 G4 按冻结**批次**审查，首批唯一原文逐项看处置理由，后续按风险分层抽检并全审异常/高风险件。`skipped_*`、`retired`、模型置信度或标题均不能单独授权删除；执行器仍逐路径核身份并保留 intent/receipt。

## 3. 严重性和裁决

| 级别 | 示例 | 裁决 |
|---|---|---|
| P0 来源/职责破坏 | 改 raw SHA/source ID、生产数据被测试写入、自动解除 Worker 暂停、向上游写投资结论、跨仓改数据库、未经许可下载 | 立即停止该卡及依赖卡，保护现场；查恢复路径。不能以新增测试掩盖。 |
| P1 证据失真 | 无来源事实、投资者提问当公司事实、编辑材料当管理层发言、计划写成已实现、retired/未来来源被消费、locator 不可回读、负例生成业务摘要 | `changes_required`，修复并重做对应负例/留出测试；本卡不能放行。 |
| P2 契约/性能未证 | schema 版本不匹配、消费者未确认、耐重启/空间/延迟门槛未测、留出集分母不明 | `blocked_decision` 或 `changes_required`；只能保留影子运行。 |
| P3 可维护性 | 文档、命名、重复逻辑不清但不影响契约 | 可要求限时修复；不得因此扩大范围重构其他模块。 |

G 节点状态只能用：`accepted_scoped`（该范围通过）、`changes_required`（有明确修复项）、`blocked_decision`（外部契约/权限/资源缺失）。`accepted_scoped` **不等于**生产发布授权。仅影响该节点结论的输入/合同变动才重开受影响审查，不把无关编辑视为全链失效。

## 4. 大节点使用的断言清单（非逐卡签收）

- **W0**：12 源 SHA、13 卡、留出集分母与盲测隔离、skip 漏收审计、数值门槛、原 v1/新附属包绑定、多原子锚/locator v2 裁决、中文短词检索合同、`retired`、as-of、消费者字段均冻结。任何 `UNDECIDED` 留在发布关键路径则不放行。
- **W1**：分类迁移不复制来源；sidecar 优先；filing-fetch 复用先行；无翻译、HTTPS 身份、下载许可和旧 US filing 回归。
- **W2**：每个原子锚能用原文 SHA 回读；P08 大 IR 表格单元可拆问答、P04 业务表不丢、PDF 正文/表格双视图覆盖、空页和跨页、TXT 两版式、编辑/发言角色、说话人不确定性被覆盖。确认页内 sort 偏移没有混入旧 normalized 游标。
- **W3**：只选细粒度业务片段；有覆盖/跳过账本与 skip 漏收抽检；13 卡通过；标准财务表与业务表明确区分；`artifact_dag.py` 的既有 dirty diff 保留并解释。
- **W4**：逐句 evidence ID、原文语言、阶段/否定/风险/角色校验；至少检查 11 正例中的关键限定词，不能仅看摘要流畅度。
- **W5**：新来源全文检索与回源有独立实现/验证，中文两字词、英文、短语、来源/时点过滤及 p95/空间通过；旧包兼容、新包身份与撤回、invalid/retired/未来来源拒绝；真实三仓的消费方各自审查其合同。任何消费者未准备好就不切换该消费者。
- **W6**：按 [并发实施手册 N0–N6](worker_parallel_execution_plan.md) 检查 R4 C05 唯一任务入口、原子 claim/finish/outbox、两库 prepared→verified→visible 对账、visible 后才 READY 的下游门禁、F01–F20、Windows 子孙清理、暂停代际、共享预算和 1/2/4 对照收益。核对新 DAG 未触发旧全量 normalize/spans。任何一个缺失只能维持单执行者/影子状态；测试通过也不自动恢复生产 Worker。
- **W7**：先用离线副本/受审工具给出表/索引和空表格单元的**实测**占用，不能凭 1000 行样本外推；迁移副本、可恢复备份、引用清单、差分查询、总磁盘字节、空间/延迟门槛、停机及回滚演练；不把清理生产 46 GiB 库塞进普通发布。
- **F0–F5 提前退役（本轮已按旧运行卡执行）**：审查 17 张目录表与 active 旧 span 精确集合、row digest/外键/`quick_check`、旧库/压缩包 SHA、`zstd -t` 与**完整解压流长度/SHA 等于原库**、active/retired 查询、消费者配置、Worker paused、峰值容量和 F5 精确文件清单。用户取消完整落盘恢复演练；收据须明列未来环境恢复未经演练的剩余风险。未来同类迁移按 G4 集中审查，不重复全文件哈希烟测。
- **D0–D5 原文处置**：在 G4 批次里核真实文件存在/卷/所有权及同 SHA 副本、全文/附件覆盖、OCR/表格缺口、正例混入负例、现有证据/检索/下游引用、版本化处置状态及删除 intent/receipt。唯一来源须明示删除后不能凭 SHA/URL 保证恢复；禁止外部 root、模糊路径和无 intent 缺失。D0–D3 不再分别签收。

## 5. 发布与回滚门禁

1. **影子发布**：只在临时 catalog 或隔离副本生成新产物；记录旧/新输出对照。W1–W6 `accepted_scoped` 可逐步扩大隔离样本，不触及生产 Worker。
2. **有限生产接入**：另开独立发布记录，明确公司/文档种类、时间窗口、开关、预算、观察指标、负责人与撤回步骤。上线动作需基于当时的现行项目门禁和用户授权；本规划不代替这些授权。
3. **失败回退**：先关闭新下载/选择/导出路由，标记新 artifact invalid/retired 并发撤回记录；原文和旧导出保持可用。消费方按契约回到已验证旧版本，不能默默继续用已撤回摘要。
4. **数据迁移**：最终冷热迁移按 W7，提前退役现存主文件按 F0–F5；均独立审查、流式备份验证、影子切换与旧文件切回，**本轮不做完整落盘恢复演练**。出现引用丢失、校验失败、active 检索证据缺失或延迟越线，F5 前切回旧文件；F5 后须另安排空间从流式校验过的备份恢复。主库缩小不代表总体空间变小，复盘须计 WAL、归档和备份。

## 6. 防止弱模型偏航的检查句

执行者在 G0–G4 收据中回答以下问题；普通代码提交只做自检：

1. “我修改了哪些文件？它们都属于本卡允许范围吗？有没有既有脏文件被覆盖？”
2. “每条新证据与摘要如何回到相同 SHA 的原文？角色、时间、否定和计划状态有没有逐项核对？”
3. “哪条负向测试会在我最可能犯的错误发生时失败？我亲自运行并看到它失败关闭了吗？”
4. “暂停中的 Worker、旧消费者、原始文档、其他仓库和生产 catalog 是否仍维持原状态？有什么可核验证据？”
5. “本卡还缺什么数据或外部决定？若缺失，我是否明确标为 blocked，而没有编造默认值？”

回答不具体，审查状态只能是 `changes_required`。跨仓所有者不回复时，维持 `blocked_decision`，不擅自替其签收。
