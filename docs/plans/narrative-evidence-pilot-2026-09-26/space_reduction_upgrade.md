# 46 GiB catalog 的降容升级方案（设计与验证计划）

> **PLAN ONLY**：不改生产库、代码或 Worker 状态。本文件补充 [实施方案](implementation_plan.md) 的 W2/W3/W5/W7，并服从现行 R4/v5 安全门禁。空间目标须在隔离副本中测量后签定，本文不宣称已能把生产库缩到某个确定 GB 数。

**2026-09-26 快路径更新**：在隔离临时库已实测“目录与全部 active 切片”仅 2.849 GiB。旧主库可以先按[提前退役审查卡](early_catalog_retirement.md)压缩备份、替换活跃库并延后清理原文件；全新选择性证据流水线随后实施。以下 S0–S5 仍用于最终冷热分层和历史消费迁移，不要求为了释放原 46 GiB 文件等到整套新流水线建好。

完整旧库的只读 `zstd -3` 流计数现已得到 **5.773 GiB**，正式备份仍未实施；用户取消完整落盘恢复演练，改以 `zstd -t` 和全量解压流 SHA/长度等于原库为 F2 硬门槛。同盘 F5 净释放预计 **37.644 GiB**，新增峰值约 **8.622 GiB**。逐步骤空间账见[空间账](stepwise_space_budget.md)。此外，新方法判定无用的旧来源**连原文一起回收**，其独立门禁见[原文处置 D0–D5](raw_disposition_plan.md)；这部分实际可删除量仍未知。

## 1. 已知事实和不能做的推断

- 2026-09-26 主库 `catalog.sqlite3` 为 **49,677,344,768 B = 46.266 GiB**；4 KiB 页共 12,128,258 页，freelist 仅 9 页，WAL 当时 0 B。现在单独执行 `VACUUM` 不会解决以大量有效页为主的占用。
- 前期只读调查约有 **2720 万**条 `evidence_spans`。以固定随机种子从 rowid 空间抽 1000 条，820 条为 table cell，496 条 `raw_text` 为空；`span_json` 平均 812.6 B。大规模逐单元元数据和三个索引是首要排查项，**全库精确表/索引占用仍未知**。
- 同一 1000 条样本的 JSON 共 812,588 B；逐行 zlib 压缩为 469,528 B，合并为一批压缩为 175,172 B（原样本的 21.6%）。这只支持“旧 span 做分源冷归档有压缩潜力”，不代表整个 DB 可按 21.6% 缩小；B-tree、索引、其它表、归档索引、原文和查询服务均未计入。
- 后续独立随机样本 1200 条（seed 20260927）中，`span_json` 平均 815.5 B；JSON 内 `span_id/source_id/locator/raw_text/parser_name/parser_version/parse_status` 均与关系列重复，估算为 418,218 B；另有 table cell 的结构值复制正文约 18,324 B。已核实两项合计 436,542 B，约占该样本 JSON 字节 44.6%。先前记载的 460,942 B / 47.1% 多出 24,400 B 且无可复核分项，已撤回。样本比例不代表全库或 SQLite 文件可缩小比例；部分空表格单元也有完整 JSON 壳。需由 S0 用全量精确统计和固定脚本确认规模。
- 实际另做两轮只写系统临时目录的旧表筛选复制：保留全部 17 张非 span 表为 214.84 MiB；再加上精确索引计数的 1,490,530 条 active span、现有索引为 **2.849 GiB**。两轮临时库均无外键错误且 `quick_check=ok`，已清理。旧查询/下游差分、正式备份及回滚尚未验证，不能把 2.849 GiB 当作已经部署的生产库。
- 当时 C 盘空闲约 77.56 GiB；两份等大主库副本需约 92.53 GiB，尚不含临时/WAL/重建空间。未准备受控独立存储或快照时，不启动 W7。
- 一次全库只读 `COUNT/SUM(locator/raw_text)` 扫描超过约一分钟仍未完成，已主动中止；不能把 1000 条抽样比例伪装成全库精确计数。当前 Python/CLI SQLite 无 `dbstat`，表/索引分解留到隔离工具或副本完成。

## 2. 两个不同的降容目标

| 目标 | 机制 | 何时体现磁盘下降 |
|---|---|---|
| **阻止继续膨胀** | 新来源只持久化 raw/manifest、轻量页/行索引、选中证据、来源摘要和紧凑 coverage；不自动运行 `normalize_catalog`，不为每个空表格单元建 span | 新文档的增量立刻变小；旧 46.266 GiB DB 文件不会因此缩小 |
| **尽早退役旧 46 GiB 主文件** | 复制全部旧元数据及 active span 为实测 2.849 GiB 的新活跃库；完整旧 DB 做可恢复压缩快照；查询/下游差分后文件级切换 | F4/F5 通过后删除旧**原文件**才释放本机空间；本地压缩备份仍占实测字节，具体门槛见[快路径](early_catalog_retirement.md) |
| **最终减少历史总占用** | 修好旧 span 冷读/引用与新证据路由，按保留期清理重复归档、备份和不再需要的派生物 | 完整数据保留策略、用户批准和净总字节验收后；不能把快路径的主文件下降当成所有历史负担已解决 |

**实测与未决**：按旧状态只保留 active span 已得到 2.849 GiB 的隔离库，这可支持提前退役旧主文件；它并未实现新业务叙述选择，retired 旧证据的冷读也未交付。完整压缩备份、既有 5.21 GB 退休归档、2.83 GB derived 与新检索索引都须计入净总占用；新流水线长期空间收益仍待 S0/S1 的相同质量实测，不能从 1000 行样本线性外推。

## 3. 新文档的空间设计

1. **保留来源的原文不变**：raw 与 SHA/source manifest 仍是可回读事实根。PDF/TXT 的页/行目录只记录位置、文本 hash、解析质量和扫描范围；廉价扫描全篇，深解析候选页与审计抽样页。不复制全文到每条 evidence JSON。确属无用且无引用的旧原文可按[原文处置 D0–D5](raw_disposition_plan.md)另行清理；删除后该来源只能保留历史身份/处置记录，不能继续宣称可回源或纳入全文检索。
2. **同一字段只存一次**：source/span identity、locator、parser/version、status 等通用字段留在关系列；JSON payload 只保存类型专属数据。正文原文只保存一份，表格的结构值可引用该正文或保存必要的结构化字段，不再复制整段 `raw_text`。通过只读兼容视图或读取适配器维持旧调用形状；只有消费者盘点和差分测试通过，才允许新格式成为写入格式。空文本的表格格子不生成独立 span；行/表级 coverage 记录解析覆盖与空值计数。
3. **选择性证据**：仅业务进展、行业、客户/产能、募投逻辑及风险、投资者问答和电话会发言等选中单元生成持久证据。业务表要保留，标准财务表可走清洗 API；表格需按内容和列义分类，不能靠 `find_tables()` 的 bbox 一律丢弃。空单元绝不作为“覆盖证明”逐格入库。
4. **低成本全文检索**：W5 先在临时库比较页级文本索引或可控按需回源，索引只返回 source+页/行候选，命中后回 raw 做精确定位。FTS5 `unicode61` 对中文词有漏检，trigram 对两字 `MATCH` 也有缺口，需单独测两字查询、英文、短语、OCR、p95 与索引字节。索引可用性和空间都未通过前不切换旧检索。
5. **冷热分层**：热层只保留当前有效来源、选中证据和必要查询索引；旧未选 span 进入按 source/hash 的压缩不可变包与定位清单。冷包支持按旧 ID 回读与校验，不能仅留下一个“已归档”标志。原文、包、manifest、活跃 DB 和必要备份的总占用一起计量。
6. **质量边界**：全篇扫描不完整时不可输出整件 skip；摘要声明只概括已选证据。选择性存储不能靠漏收来省空间，W0 锁定分类型召回和被跳过文档漏收的正式样本量/置信区间。

## 4. 旧库迁移的实际顺序

| 阶段 | 必交付验证 | 禁止动作 |
|---|---|---|
| S0 精确盘点 | 离线/受审工具按表、索引、source 状态、段落/表格/空单元统计页字节；列出旧 export/query/下游引用；测原文+DB+WAL+归档+备份总字节 | 用抽样比例直接决定删除范围 |
| S1 新路由止增 | P01–P04 隔离旧/新双跑；IR、负例与 TXT 用绝对新增字节；同等召回、定位和查询能力；新路由不产生旧全量 normalized/spans | 只测摘要质量、不测全文查询和空间 |
| S2 冷归档试点 | 选一个原文 SHA/来源版本明确、引用可枚举的小批；写压缩包、每行/包 hash、可回读索引和恢复收据；原文/旧 DB 保持不动 | 调用现有自动 prune 作为捷径；R4/v5 的 H01 风险未关闭 |
| S3 紧凑库影子重建 | 在**空间足够的独立卷**重建 source/manifest、当前选中证据、搜索索引和归档目录；旧 ID/撤回映射；逐查询/逐导出差分、断电/中断恢复演练 | 在生产 DB 上批量 DELETE、原地 VACUUM 或覆盖旧文件 |
| S4 双读与切换 | 旧/新读者同输入对比，按公司/类型灰度；停止新写旧全量路径；监测 p95、缺证据、空间增量和冷读取；签名切换及回滚 | 消费者未迁完即删除旧 span 或声称节省已兑现 |
| S5 保留与回收 | 只有引用/保留期/恢复演练均过，才按独立迁移审批卸载旧主库或旧归档；报告活跃库、冷包、备份的净总字节 | 把“主库变小”当成“总磁盘变小” |

现有 `archive_retired_evidence` 已采用 gzip JSONL，但其筛选条件仅覆盖 `source_status='retired'`；活跃来源中未选的全量 spans 不能直接套用该工具。Worker v5/R4 对自动 prune 的 H01 风险另有独立硬门禁。归档功能存在不等于能安全自动删旧行；S2/S3 必须先定精确 PK/hash/引用与恢复合同，沿现行专项计划修复或保持硬禁用，不能绕过。

## 5. 小范围量化试验及决策表

在**临时 catalog/独立卷**复跑 P01 年报、P03 季报、P04 招股书；P08 IR、P09 制度 PDF、T01 TXT 用于验证新类型和 skip。记录每件 `旧/新持久 span 行数、空 table cell、normalized/sections/package 字节、SQLite 主库+WAL+索引增量、搜索索引字节、查询 p50/p95、解析/模型时间、证据召回与引用错误`。同样的输入、parser/模型版本、机器和缓存条件重复三轮，成本与质量一起报告。

| 结果 | 决策 |
|---|---|
| 新入库永久派生字节明显下降，且分类型召回/locator/中文检索门槛均过 | 可以继续扩大 S1；W0 在看候选结果前签定“显著下降”的百分比，建议以 **至少 80% 派生字节下降**为挑战目标，未实测前不作为承诺 |
| 只压缩包小，搜索索引/缓存抵消大部分节省 | 调整索引粒度或冷热层；按**净总字节**重新裁决 |
| 活跃库缩小但旧归档+双备份仍使总占用增大 | 不宣称 46 GiB 问题已解决，先审查保留政策和独立存储 |
| 召回、业务表、IR 问答、中文两字词或历史 v1 查询失败 | 保留旧读路径，停止切换；禁止为达空间目标放宽证据门槛 |

**优先级**：短期按[快路径 F0–F5](early_catalog_retirement.md)验证活跃库与完整压缩备份，争取提前退役 46 GiB 原文件；中期 S1 止增，S2–S5 负责历史消费、最终保留和净总字节。两条发布线与 Worker 并发上线分别审查。

逐份跳过的旧文档另有[原文处置 D0–D5](raw_disposition_plan.md)：Worker 的零切片只产生候选，不自动删除；经完整覆盖和消费合同审查后，可清理同 SHA 的旧重复副本或唯一的低价值原文。D0 必须按真实路径/所在卷测字节；现有 catalog `observed_size`、`retired` 数量都不能直接当可释放空间。

## 6. “旧纪录全部删除、从头再来”审查

### 结论

**从空 catalog 按新方案重建，可能比逐行修补旧 schema 更清晰；但先删除再重跑并不更干净。** 只有先完成新写入路径、隔离重建和新旧核对，才能判断它是否适合替代旧库。若用现有全量 `normalize_catalog` 重建，系统会重新生成 normalized Markdown 和逐段/逐表格 EvidenceSpan，46 GiB 的形成机制仍在，空间问题会回来。

### 可重建数据与必须保全状态

只读核验当前配置后，四个输入 root（company raw、dayu portfolio、Dropbox Stock、future lake）都可解析且路径存在；配置将它们声明为只读输入。`source_manifests/` 也在 `.source_catalog/` 之外。项目文档说明 normalized/summary、SQLite、派生物和索引写入 `.source_catalog/`。因此原始文件足够可读时，文档 hash、当前来源位置和**新方案定义的**紧凑解析结果可以在影子目录重建。

但 `.source_catalog/` 不是只有 46 GiB 的结果库。它还混有 `worker_control.json`（desired_state/暂停控制）、`worker_state.json`、运行/启动事件、`worker_runs.jsonl`、抓取尝试/重复清理审计、security master 缓存、导出索引、队列暂存与运行锁。**不得删除整个目录**；这会清掉审计/恢复线索，并可能让新的默认控制状态不再是原先的 paused。控制与审计状态必须按版本保留，Worker 暂停须在任何影子运行及切换期间逐次验证。

清空后还不能从现存文件恢复所有历史语义：已经从输入 root 消失的来源、retired/missing 状态转移、过去的下载尝试、旧 source/document/artifact ID 引用及某些外部消费者快照可能不在 raw 文件中。扫描器按既有规范把路径消失标为 `missing` 并保留历史记录；重建成空库不会自动得到这些 tombstone/history。按 SHA 派生的 source ID 可能稳定，但它不替代对旧 artifact ID、撤回、时间状态和消费者缓存的映射审计。

### 首选路线：新方案先隔离重建，后评审替换

| 步骤 | 要做的审查/验证 | 放行条件 |
|---|---|---|
| R0 范围与状态封存 | 记录生产 DB/WAL/SHM、`.source_catalog/` 全部顶层子项与大小；保存现有 Worker desired_state、运行状态、catalog schema/version、控制日志、获取/清理审计、导出 ID 和 hash。精确区分 raw、sidecar/source manifest、派生物、运行状态和临时文件 | 清理候选为显式白名单路径；没有“删除整个 `.source_catalog`”或宽泛通配符 |
| R1 来源可重建性 | 对每个旧 active/retired/missing 来源核对 raw 可访问性、SHA-256、sidecar/manifest、实体/类型/发布日期；列出无法重建的记录和消费者引用 | 所有有效来源的原文与 manifest 有可验证备份；无法恢复的历史来源已单独保留/登记，不被当成无用数据 |
| R2 新格式门禁 | 在临时目录固定新 schema、选择器、摘要、locator、coverage 与检索合同；实现单份正文、通用列/JSON 不重复、空 cell 不建 span；运行 P01/P03/P04/P08/P09/T01 与冻结留出集 | 业务证据、IR 问答、招股书业务表、回源/中文检索及历史时间过滤达到预注册门槛；无旧全量 normalize 的隐式调用；字节统计能拆到各类产物 |
| R3 干净影子重建 | 把 catalog 输出指向新隔离目录，从只读输入 root 重扫；只写新 schema；日志、产物和重跑结果可复现。独立核对源 SHA 集合、状态差异、证据召回、locator 回读、export 与运行后目录大小 | 每个差异可解释；重复重跑幂等；中断/重启可恢复；Worker 不从影子配置意外启动；新 catalog 达到空间和性能门槛 |
| R4 双读与消费核对 | 对照旧/新同一批查询、导出、下游引用；建立旧 ID→新 ID 或明确 tombstone；核对撤回、retired/missing/as-of 和历史快照；保留只读旧库以便回滚 | 三个下游消费者的合同/夹具各自通过；关键引用零丢失；独立审查者签 receipt；有已演练的切回步骤 |
| R5 替换与延后清理 | 明确生产切换窗口，先切换路径/索引再监测；旧库只读保留到观察期与恢复门槛结束。清理时按确切 DB 文件及其 WAL/SHM 状态做独立核验，不碰控制、日志、manifest、原文和其他目录 | 另行明确批准确切清理对象；有可用恢复副本/外部保留策略；报告主库、旧备份、新库、raw、索引和总占用变化 |

### 决策建议

若能先完成[快路径 F0–F4](early_catalog_retirement.md)的活跃子集核对、完整压缩备份恢复、旧查询的明确归档提示和下游差分，原 46 GiB SQLite 文件可**早于**新生成器上线而退役；这样更快释放本机空间。若任何快路径门槛不通过，则回到 R2/R3 的完整影子重建，不直接删旧库。F5 清理批准必须精确到旧文件的路径/大小/hash，不能把对新设计的认可视为删除授权。

容量仍是前置限制：C 盘最新空闲约 79.217 GiB；旧库 46.266 GiB、活跃子集实测 2.849 GiB，完整 `zstd -3` 只读压缩流 5.773 GiB。正式快照与恢复未验证；若恢复临时文件也在 C，新增峰值估算 54.888 GiB，尚未计 WAL/安全余量。应按每一步的实际峰值与余量决定是否使用独立卷；不能通过先删唯一旧库来规避空间预算。全程保持 Worker 暂停。
