# 测试暴露问题的根因修复规则与分组施工

2026-10-08 用户明确要求：每个问题追到产生它的机制，从责任层修复，不能逐公司打补丁。本文件约束 follow_up_plan 的全部后续施工；原始失败、固定基线和独立复查记录保留。

## 一、如何判定修复完成

每个原 issue ID 对应一个责任组。组内记录六件事即可：原症状/证据、最小复现、已证实根因及未证实假设、责任层与共用改动、原测试为何漏报、修复前后结果。直接引用原审查/命令账，不另建审批、合同签收或重复状态库。

1. **找机制**：区分业务契约、数据/元数据、配置/安装、执行顺序、供应商限制、测试自身。仅看到错误码不能宣布底层根因成立。用最小反例和受控变量验证因果；修复某条件后错误消失，还要证明相关语义没被关闭。
2. **先写责任测试**：最小用例须在旧实现失败，并覆盖同类变体和合法正例。跨进程问题必须跨进程；合法 SHA 但语义错必须有语义反例；来源能力必须实测公开入口。禁止复制实现算法再比同一结果来证明正确。
3. **修复共用层**：先找所有调用方和同类机制。CWP 负责来源/规范化/存储/定位，FF 负责调用编排，ET/市场 provider 负责各自能力，RF 负责研究输入/计算/产物。对 MSFT 的特判、绕过 FF 人工抓取、把物理目录细节加到 RF，都不算完成。
4. **保留有效不变量**：原件和旧快照不可改写；身份、期间、可用信息日、实际预算、证据含义继续检查。不用删测试、改成功阈值、强制同一 hash seed、补虚构日期、统一放宽校验来掩盖问题。若测试或契约确实错，先记录独立来源/数学依据及新的错误反例，再修改；旧基线仍留存。
5. **一组一个大节点**：责任层单元测试 → 公共接口集成 → 三家公司相同定义的 full replay/compare；涉及采集再运行隔离 live，涉及新研究再运行三执行/独立复查。所有调用恢复独立测试目录。平时 CI 保持轻量，不给每个小改动新增人工审查。
6. **不误报关闭**：子进程没启动、供应商无权限、样本缺失、没有实际消费或未来真值，分别保留 NOT_RUN/BLOCKED/NOT_APPLICABLE。接口正确但供应商不可用只能关闭代码问题，不能把真实数据能力签为 PASS。

## 二、当前问题分组与根本修复方向

下表是施工分类，详细证据仍见 findings、固定检查点和三个独立复查；“已证实”仅指表内事实，不表示改造已实现。

## 三、实施顺序与下一步

1. 先做 P0 RF 稳定计算，补最小 RED/跨进程证据后确定兼容策略，再改共用实现及安装闭包。大节点须把原 process_seed_stability 从 FAIL 变为 PASS，其他 70 检查无新增退化。
2. 接着做采集能力与错误传播：CWP-owned bounded 桥、FF/ET 能力/费用分流、来源元数据资格。可以按责任仓分组施工，但主线统一验证调用链；供应商限制如实留下。
3. 再完成共用格式规范化和 RF 输入/证据构建、摘要实际消费，最后重跑完整新研究及独立复查。

每组开始前将原 issue ID 映射到上表，新增失败也归到责任组；需要改变分组时记录因果证据即可。相同模式/样本/定义保留前后比较；若能力扩展必须增检查，旧 71 项照跑且新增项单列。这里没有新增人工许可或逐小节点签收。
