# 第二组三家公司：全部改造后的泛化验收

2026-10-08 用户要求：全部完成后再换三家公司跑完整端到端，检验是否只针对第一组公司修复。第一组中微/腾讯/微软继续作固定回归，不替换其清单、原件、独立审查或基线。

## 触发时点与责任

root_cause_remediation/follow_up_plan 的代码和配置改造完成并发布后执行。先重跑第一组 full/live，明确仍有的供应商或数据限制；随后固定待验收版本，在新样本上跑本卡。MAIN 负责选样、统一接口和结果归总；三个执行 agent 和独立 review 按原 common_execution_contract/independent_review_contract 运行，分别独占自己的测试目录。这是一个最终大节点，不新增逐小步骤人工签收。

## 1. 选样并固定，防止挑容易通过的公司

- 新选 A 股、港股、美股各一家，均不得是中微、腾讯或微软。执行前按本地只读资料清单和官方公开资料核实选择理由、证券身份与测试信息日，不现在凭印象指定公司或文档年份。
- 尽量换主营业务及收入驱动形态；至少一例本地有合格原件可复用，一例对应期次在独立测试 catalog 中确实缺失且需要真实下载，不能把故意隐藏生产库文档称为“全机没有原件”。两种情况分别记录。
- 三家公司合起来覆盖年报/中期或季报、投资者沟通/电话会原语言 TXT、SEC HTML，以及适用的招股/增发/可转债业务描述。图片型资料也使用真实样本检查；公司无此类型时给出具体不适用理由，不能因此删除共用格式测试。
- 选定后先保存 selection.json：entity/market/security ID、业务差异、as-of、已知本地存在性、计划复用/新下载的精确期次及类型、provider、关键边界案例、预算和运行版本。固定三家公司后遇到失败保留该样本；不得悄悄换成更易通过的公司。若公司/资料事实不符，记录更换依据并保留失败记录。
- 固定来源实际字节与可验证的历史金额/单位/期间/目标/公开日，作为独立事实 expected。不把新引擎结果或执行者输入倒过来当事实 oracle，也不预先虚构未来预测的正确答案。

## 2. 独立运行完整链路

- 新随机 owned 测试环境，隔离 CWP catalog/DB、AUTO/work、RF registry/output、HOME/缓存；只读已有原件，按需复制测试样本。全新来源经既有正确市场 provider 下载到隔离 CWP 公司目录。Dayu 零改动，邻仓 WIP 不参与。
- 实际跑 RF→FF→CWP→SID/Dayu，以及适用的 FF→ET→CWP；验证实际启动、费用/字节/时间限额、入库 SHA/身份/期间、重复请求零下载和现有电话会零重复抓取。不把手动网页下载或离线 fixture 当线上路由成功。
- 真 canonical 解析/业务精选/有限摘要/虚拟读取；原语言、不翻译。新 NarrativeRef/claim/span 必须能追到进入 RF 输入的参数或 driver，文件存在不等于消费。套话/纯格式文件的跳过理由及有价值业务描述的召回分别检查。
- 完整 RF 技能 0–11，包含历史、管理沟通/目标、独立基准、情景、桥接、敏感性、置信度、正式 JSON/Markdown、快照和登记账。未来实际未知的回测明确不适用；不靠生成一份新报告冒充这些步骤。
- 沿用当时已配置的 MiMo/DeepSeek/MiniMax profile 和已批准累计预算，不重置费用账、不临时换模型或追加订阅。所有 start/finish、命令/子进程、失败、输出 SHA 与调用费用记录。测试退出后恢复原状，只留轻量清单、日志和最终必要交付，避免再永久复制全量中间件。

## 3. 相同原则，独立事实与审查

沿用第一组 23 个公司级检查点和 2 个共享检查点的责任含义。第二组清单中的格式/事实 expected 改为新公司的真实资料；不修改第一组封存的 checkpoints.json。保留代码共用检查点 ID，适用性逐项说明；公司名相关的描述不能成为运行条件或绕过规则。

- 工程检查：原件/旧快照不变、真 provider/FF/ET 调用、SourceRef 物理移动仍读、坏 hash 拒绝、复用幂等、定位回放、原语言摘要、正式产物/registry 强绑定、多 seed 跨进程稳定、真实预算及故障清理。
- 事实/语义检查：重新打开所有引用原文上下文，审金额/单位/期间/分部/并表范围、管理目标、ratio/pp、季度/年度和 CC/reported、同行证据角色、分析假设及反证；确认最新材料和技能步骤没有遗漏。使用三个独立 reviewer，不能只对执行报告或引擎成功码签收。
- 泛化检查：审查共用实现/配置是否有 ticker/company/source SHA/文档固定页码特判。实体别名、事实清单属于测试资料，不能把第一组答案塞到运行代码中。用不同权重/段落结构/文件名/页数验证同一接口机制。
- 若新样本发现问题，先补最小通用失败例，回到对应责任层修复；再跑两组相关责任测试和集中 E2E。保留首次新样本失败版本，不将其删掉后只报修复后结果。

## 4. 交付与比较

记录在独立目录 `docs/plans/cross-market-rf-generalization-<实际运行日>/`，不要提前创建空执行记录。最少交付 selection.json、task_plan/findings/progress、executions/{company}、reviews/{company}、新组 cases/checkpoints、第一次实际结果、修复后结果（如有）、acceptance_summary。参考既有审查 JSON 格式，不增审批合同。

第一组自身前后 compare；第二组自身前后 compare。两组 samples/spec SHA 不同，禁止直接用 runner compare 的数值变化宣称改善，禁止把不同公司预测金额作相等断言。跨组总结共用检查点的通过/阻塞/未运行、责任机制覆盖和完整研究审查结果。

全部结束时报告两组各自结果、原件/配置保护、临时环境恢复、累计费用与空间、未解决限制。关键工程或语义错误未解决时不得宣布泛化验收通过；供应商客观不可用独立列 BLOCKED，不能冒称代码失败已经修复就等于真实采集成功。
