## 共因与实现

原 `stockwiki/_source_reader_v2_transport.py::open_verified` 使用 `subprocess.run(stdout=PIPE, stderr=PIPE)` 收完两路后才判断 stdout 长度，stderr 没有限额。仅最终拒绝成功不能约束读取期间内存，也不能证明超时后的后代进程已回收。

现在复用 **StockWiki 自己已有的** `_narrative_process.run_bounded` / `_narrative_process_tree.ProcessTree`，没有新建 runner 或 import CWP 私有模块。这个模块名保留历史 narrative 名称，但本次仅复用其受限管道/进程树基础设施，不调用任何叙述研究业务、数据库或模型。

- stdout 使用原配置 `max_stdout_bytes`；stderr 只承载单个 receipt，明确固定上限 256 KiB。
- 读取期间计数，最多读取 limit+1 即中止；Windows Job Object/Posix process group 回收整个本次创建的进程树；既有共享 deadline 和清理预算继续生效。
- runner 的命名失败转成既有 `SourceExportV2Error`，保持 receipt/manifest/字节 hash 交叉验证。移除内部 runner 已保证后的冗余末端长度检查。
- `scripts/checks.py::SHORT_TESTS` 只增加两项新回归所在文件；未把完整 CLI/E2E/全量测试搬回日常流程。

改动仅三个 StockWiki 文件：

1. `stockwiki/_source_reader_v2_transport.py`
2. `tests/test_source_export_v2_bounded_transport.py`
3. `scripts/checks.py`（日常清单一行）
