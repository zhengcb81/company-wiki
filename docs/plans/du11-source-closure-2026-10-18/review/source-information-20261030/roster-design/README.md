# 产品清单、客户链与上市流程：只读设计意见

2026-10-30。只读当前共享 owner 及保存的 actual-roster-observations.json；不修改正在终审的 QA 八文件，也不签后续实现/真实金标通过。正确拆 QA 后失去旧的跨段“借业务支持”，暴露出独立来源语义缺口；不能以 span 数变小作为质量改善。

## 明确结论

1. **产品/业务构成缺完整 composition/copular grammar。** `_clause_description_proofs` 对中文产品 head 后支持提供/包括/包含/制造/状态等，却不支持“主要产品为……”这一来源自足构成关系；actor-first provision 又偏向通称公司。中性“公司主要产品为精密设备、传感器和光学材料”与换名“澜芯材料主要产品为……”均 payload=None、fact不可用、relevance=False；改成“公司提供……”就支持。因此不能只修具名主体归属，更不能增加某种化学品名。
2. **产品→客户类型→客户的下游类型，是来源描述关系，不必先解析成发行人身份。** 未知 named subject 的内容仍可有独立来源价值；保留原主语及未知归属，不替换成本公司/上市主体。真正的关联方归属依赖同源明确声明，不能由投资者问题或名称猜测提供。现有完整客户链缺少 copular/链式关系，不能再借邻近产能段恢复。
3. **上市问询/中止/条件恢复缺 process-aware 来源语义，当前样本不是被财务词吞掉。** 仅改名的完整“收到二轮问询→因资料过期申请中止→更新后将申请恢复”与删去“财务数据”的对照，都得到 financial=False、purpose unknown、payload=None。不是再调 financial_only，也不是扩大融资章节路由；是正文断言没有被表示。
4. **经营影响否认也是独立关系缺口。** 改名“据相关报道，该事项未对澜芯材料经营构成重大影响”仍无独立支持。其可提取内容是管理层对某事项影响的否认，不能反向把新闻/提问中描述的事项当已经证实的事实。

### 一个会误导测试的现有假阳性

同一短探针中，“澜芯材料主要产品为发光薄膜材料，下游客户为**显示器件制造企业**”当前会得到 support，而原文“成品材料**生产企业**下游……”不支持。不能把这个绿当作 composition grammar 已覆盖：`_CN_FUNCTION` 有“制造”，使“器件制造企业”有机会被解释成器件在制造企业这一动作。新增构成语法时必须有**生产/制造企业作名词修饰**的对照，禁止把客户类型名词误当经营动作或“制造企业”的产品功能。

本次只执行 7 个短同 SourceOperatingSession 改名/改谓词/有无财务资料的输入，无全域/PDF/SDK/模型/下载；上述真假对照来自实际工具输出，而非推测测试已通过。保存原四项真实孤立观察仍是基线，不覆盖其历史结果。

## 最小泛化方案：仍由一个共享来源 owner 准备

### A. 在现有 prepared assertion 中增加类型化描述关系

由 `operating_states/assertion_roles.py` 的 clause/proof 路径准备，必要时把这一组纯函数抽为同包私有小模块；不在 QA helper、selector、摘要 prompt 各复制一套识别规则。

- 构成 frame：**实际主体/其产品或业务 head → 为/主要为/包括/consist of 等构成谓词 → 有内容的成员列表**。列表成员可以是陌生名称，不能要求全部进入产品字典；正面证明来自来源明确的产品/业务构成关系，而不是“未知词算产品”。纯“各类优质产品/全面服务”仍由现有 abstract-argument 三态判断，不因为有“主要产品”就直接支持。
- 客户/下游 frame：**本地已述产品/主体 → 下游客户/用途 → 来源给出的客户类别**，后续每条边各自保主语。不能把 A→B、B→C 压成 A 与 C 有直接销售关系；名词“材料生产企业/器件制造企业”是客户类别，不产生 production/delivery 事件。只有真实局部省略/指代依赖，才沿当前 QA 闭包保必要前文。
- 具体名单/数量可以形成可摘录的描述或研发里程碑，**不制造进展阶段**：“已销售的产品主要为……”与“已开发超300种……”分别保销售清单/已开发状态，不能推成300种均已销售、批量生产或贡献收入；领先水平是管理层自评，不能由它证明客观行业排名。
- 把这些观察输出到现有 SourceAssertionRoles 的独立 payload/witness/material 分类，再由 ReadingBusinessAssessment、source_support_use、relevance/value 共用。静态构成事实不需要硬套量产/认证状态；每个物种是否具 named entity 类别仍可 unknown。

`SourceOperatingSession.source_text/maps/_original_refs` 继续负责范围与原文引用，MatchingView 继续负责规范化到原文映射。新描述关系不能靠 normalized witness 的字符串查找创建 locator。问句、新闻转述和管理层自己的断言保持来源角色差异。

### B. 添加有过程对象的 regulatory/source-event frame

同 prepared 来源语义层观察**主体＋过程对象＋步骤/状态＋模态/条件**。过程对象须明确为上市/发行/审核问询等；它是来源信息，不是投资研究结论。可作为同断言 owner 的一个关系族接入，不新建 regulatory provider、独立 skill、第二选择引擎或状态库。

- `已收到审核问询函` 是收到这一事件，不是通过上市审核；日期只取原文，不补年份。
- `已申请中止审核` 首先是已提交中止申请，不能未经来源证明就改为交易所已批准、已暂停；若原文明确当前审核中止，再记录该流程的 suspended 状态。
- `待资料更新后将申请恢复审核/回复问询` 是带条件的未来申请/回复，不是已恢复审核/已回复，更不是已经获批上市。
- 悬停/恢复的对象始终是**审核流程**，不能落到 production suspend/stop，也不能变监管拒绝/撤回上市，除非原文明确这么说。
- 财务资料更新在该 frame 内是程序条件；不是纯财务结果卡，也不因出现“财务”就否决整段。财务审计/会计政策、一般资料报送、泛“遵守监管要求”并不自动成为有用上市进度。
- 若沿现有 relation extractor 扩展，要保留其未知/否定/条件及 reported-proposition 边界，不对通用 administrative-receipt guard 作全局豁免。不能只把“中止/恢复”加入一个无对象状态词典。

目的/主题投影使用既有 purpose/facet 责任层；确需新的 process purpose，应在同 owner 定义并通过既有兼容路径，不把来源正文重新路由成另一类文件。IR 中讨论子公司上市、本身就可以有价值，不要求整份文档必须是招股书才能识别该局部事实。

### C. 经营影响的肯定/否认沿同一局部关系

准备 `事项/事件 → 对哪一主体或经营范围 → 影响及其极性/程度`。原“未构成重大影响”不等于完全没有任何影响；“据报道/您描述的情况”保转述范围。主体实体类别可未知，原文主体仍须保留。没有具体事项、对象或影响断言的泛套话，不给独立 payload；“未对财务报表有重大影响”等会计目的也不能仅凭“影响”入业务卡。

## 先 RED 的中性正反例矩阵

| 组 | 正向输入 | 必须保留的控制/不变量 |
|---|---|---|
| 1 构成 | 公司/换名主体主要产品为多项具体材料/器件；繁体及英语同义 | 通称与专名同义；未知归属不抹掉内容，也不变发行人；仅名词清单/标题/问句不能冒充断言 |
| 2 列表质量 | 实际售卖的产品清单、子集/非穷尽“等” | “各类优质产品/全方位服务”不成为具体清单；“主要/包括/等”不变完整全集 |
| 3 研发数量 | 同一具体业务范围已开发N种成果，另句实际销售清单 | 不能把已开发=已销售/量产；数字角色/单位保原样，不追加收入换算；孤立未知“开发N个X”不因数字直接 qualified |
| 4 客户链 | A产品的下游为B类企业，B类的下游为C类 | 保两条边，禁止A→C直供推断；“生产/制造企业”是名词类别，不产生行动 proof；缺局部主语则闭包/partial |
| 5 来源归属 | 管理层陈述某具名关联主体的产品/客户；真实同源别名 | 问题提到的“子公司/主要客户”不成为事实；未知关联关系保未知；不把第三方进展当发行人 |
| 6 影响否认 | 所述事项未对某公司经营构成重大影响 | 保“重大”的程度与否定；不把报道前提洗实；纯会计影响/无对象套话不支持 |
| 7 审核阶段 | 收问询→申请中止→资料更新后拟申请恢复 | 分别保事件/申请/条件未来；不变停产、监管拒绝、已恢复或已通过；有无“财务数据”不改变过程对象 |
| 8 错过程 | 上市审核/产品认证/生产停工/财务审计几种同形“中止/恢复” | 过程与状态绑定；一般收到文件/监管套话/会计政策保持非独立业务支持；问句/假设/转述不成实际状态 |
| 9 隔离复验 | 每一项独立 source owner、再经 QA scope→公共task/card | 必须独立入选相应内容，不借产能/另一回答证明；关键事实丢失不能因总span下降签通过 |
| 10 资源/闭合 | 长名单、句中截断、枚举尾部未读、原文断片 | 工作先计费，payload未知不判无用；不把每个名单词重复扫全句；locator/原件/已冻结QA接口不改 |

## 建议实施顺序

1. 先冻结孤立 owner 的 composition、名词修饰假阳性、regulatory 过程有/无财务资料及影响否认 RED；同时保现有技术功能/会计/未知制造控制。
2. 修同 prepared assertion/局部关系 owner，消费者只读已准备结果；不在 QA scope 插产品白名单或给整个答复例外。
3. 通过短测后，从保存的同批 parsed 重选，逐项比较 roster、300成果、客户链、审核条件及否认的实际引用与角色；原四条真实基线保留。既不能为找回它们恢复全 QA support，也不能误删本来需要的前文。
4. 一个大节点做独立审查和受影响域检查，再实际 task/摘要检查。纯工程绿、能读到原词、或改名案例偶然 support 均不等于真实内容验收通过。

本次意见已明确落盘，未开展全域研究或实施；ROOT 归入选定 PWF 后按其主线继续。
