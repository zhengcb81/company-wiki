## 已验证的首批工作

- **CWP 配置边界。** 已有增量摘要端到端改为在新进程禁用旧顶层脚本导入，并检查命令不改搜索路径。旧版可复现失败。修复后实际运行 `read-incremental`，本地 HTTP 替身首次收到一个调用，重启后复用原 artifact，配置暂缺时仍读回缓存和真实累计用量。保留旧脚本 alias，同一 config loader 保持凭证优先级。独审发现 dotenv 注释/引号的兼容差异，已复现、用原解析器修正并独立复验。新增的无 editable 安装、仅旧脚本位于导入路径的反例也已修复。第二个真实入口验证配置化批处理和重启，按阅读 owner 的当前公开类型验收，原有字节、摘要引用、计费及清理断言保留。合计 90 项通过，测试目录已清理。Ruff 通过，mypy 全 511 个包源码文件通过。
- **CWP 存储生命周期。** 原重复采集和去重断言已通过，但 Windows 删除测试库仍报 `WinError 32`。起因是夹具没调用目录 owner 已有的关闭操作，现由创建夹具负责关闭。另有独立的生产问题：真实 SQLite 写竞争使批事务启动失败时，存储之前会留下活跃标记，同一实例之后无法重试。测试用第二个连接持锁复现；现在先取得写锁，失败时关闭本次连接，解除竞争后同实例重新提交成功。五份相关测试共 38 项通过，临时目录清理完成。
- **CWP 下载值契约。** 原文写入、供应商适配与纯值的命令入口原先经 `acquisition` 顺带加载采集协调器。冷 Python 进程复现后，把回执、候选和发现分页移到纯值模块。写入器和只消费值的模块直接按同一类型工作，原模块和包级路径仍导出相同对象。独审 AST 对照原来的校验、版本和字段语义，并独立验证真实冷启动。123 项合同测试、512 个源码类型检查及 Ruff 通过。`82b38ad09` [精确 CI](https://github.com/zhengcb81/company-wiki/actions/runs/45575373728) 通过。
