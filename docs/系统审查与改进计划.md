## 二、根本瓶颈：信息流是熵增的

当前流程：

```
PDF → 一次 LLM 摘要 → wiki 条目（原始信息 99% 丢弃）
```

每一层都不可逆、不可重处理、不可验证。wiki 会越膨胀越不可读，但原始信息已经损失——这就是"为什么多轮改造仍然失败"的根因。

llm-wiki.md 要求的"复利增长"需要的是**熵减系统**：

```
采集 → 提取信号 → 验证 → 压缩为判断 → 淘汰过时信息
```

当前只有前半段（采集→提取），后半段（验证→压缩→淘汰）全缺。所有的"进化模块"（event_bus、job_queue、repair_planner）只在做前半段的事——它们不压缩、不淘汰、不产生判断。

## 三、核心改进：三层数据架构

### 3.1 设计

从根本上重构数据管道，让信息在每个阶段可保留、可追溯、可重加工：

```
Layer 1: raw/PDF         — 原始文件，不可变
Layer 2: extracts/MD     — 全文无损转换，保留页号
Layer 3: segments/SQLite — 标签化分段，不删减原文
         ↓
       wiki 合成（可重跑、可换策略）
```

**Layer 2 格式：**

```
companies/{公司名}/extracts/
  2024年年度报告/
    full.md          ← 逐页保留的全文
    metadata.yaml    ← 来源PDF路径、页数、提取时间
  2025Q1季报/
    full.md
    metadata.yaml
```

`full.md` 内部保留页号：

```markdown
## 第3页 | 公司简介和主要财务指标
...原文...

## 第4页 | 管理层讨论与分析
...原文...
```

**Layer 3 标签体系（多维分层）：**

| 维度 | 标签示例 | 用途 |
|------|---------|------|
| 实体 | `公司:北方华创`, `行业:刻蚀设备`, `产品:ICP刻蚀机` | 精确检索 |
| 内容类型 | `业务回顾`, `财务数据`, `前景展望`, `风险提示`, `管理层讨论`, `研发进展`, `产能规划`, `客户分析`, `竞争格局`, `政策法规` | 按分析需求筛选 |
| 时间 | `报告期:2024`, `展望期:2025H1` | 区分历史和预测 |
| 来源 | `来源:年报`, `页码:45-48` | 溯源 |

**Layer 3 存储（SQLite）：**

```sql
CREATE TABLE segments (
    id INTEGER PRIMARY KEY,
    source_path TEXT,         -- Layer 2 MD 路径
    company TEXT,
    section_title TEXT,
    page_start INTEGER,
    page_end INTEGER,
    report_date TEXT,
    content TEXT,             -- 原文完整保留
    char_count INTEGER
);

CREATE TABLE tags (
    segment_id INTEGER REFERENCES segments(id),
    category TEXT,            -- entity / content_type / temporal / source
    value TEXT,
    PRIMARY KEY (segment_id, category, value)
);
```

### 3.2 优势

1. **可重处理** — 换了分析框架不需要重读 PDF，从标签库重新合成
2. **可验证** — Layer 2 可逐页对照原件，Layer 3 可逐段对照 Layer 2
3. **信息不坍缩** — 标签只做索引，原文无损保留
4. **低成本** — Layer 3 标签化一次性成本 $200-400（4,547 份 × $0.05-0.10），增量成本极低

## 四、详细改进计划

### 原则

### Phase 2：重建数据管道（约 10 天）

#### 2.1 Layer 2 批处理（3 天）
- **新建**：`scripts/build_extracts.py`
- **功能**：遍历所有 `companies/{name}/*.pdf`，调用现有 `pdf_extract_v2.extract_pdf_text()`，输出 `full.md` + `metadata.yaml` 到 `companies/{name}/extracts/{报告名}/`
- **验证**：所有 PDF 的对应 MD 均生成，页号标记精确

#### 2.2 Layer 3 标签化（4 天）
- **新建**：`scripts/tag_segments.py`
- **功能**：
  - 读取 Layer 2 `full.md`，按章节/页分割段落
  - 调用 LLM 对每段标注多维标签（从规范字典中选择）
  - 写入 SQLite `segments` + `tags` 表
- **依赖**：建立 `config/label_taxonomy.yaml`（30-50 个标准标签）
- **验证**：随机抽取 50 段，人工审查标签准确率 > 90%

#### 2.3 适配 ingest_v2（2 天）
- **文件**：`scripts/ingest_v2.py`
- **改动**：增加模式 `--source=segments`，从 SQLite 标签库取料（而非直接读 PDF/raw），LLM 的输入从"原始 PDF 文本"变为"已标签的结构化分段"
- **验证**：对已有 ingest 结果的页面，新模式产生等效或更优的输出

#### 2.4 接入 scheduler（1 天）
- **文件**：`scripts/scheduler.py`
- **改动**：在 PDF 下载后自动触发 `build_extracts` → `tag_segments`；`ingest` 步骤优先使用 segments 源
- **验证**：scheduler 运行一次完整管道不出错
